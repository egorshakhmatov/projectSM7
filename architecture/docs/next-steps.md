# Следующие шаги команды

На текущем этапе согласуются архитектура и границы частей программы. Ответственный за архитектуру может завершить проектирование без готового CSV. Следующий этап — подключение модулей и проверка всей цепочки.

## Что подготовлено

| Пункт первоначального плана | Результат |
|---|---|
| Постановка задачи | Основа — ТЗ версия 2; горизонт 5 минут, окно 12 × 3, ответ — номер светофора |
| Общая схема | Два независимых пути: подготовка модели и прогноз по сохранённым весам |
| Модули | Назначения, зависимости и будущая структура исходного кода |
| Алгоритм | GRU 32, правила обучения, выбора класса и сравнения с базовым алгоритмом |
| Инфраструктура | Локальный CPU, единый запуск, отдельные команды для проверок |
| Передача работы | Форматы данных, модели и результатов в interfaces.md |

## Ближайшая работа ответственного за архитектуру

1. Обсудить с участником по данным границу из `interfaces.md`: исходные единицы X, порядок признаков, метки 0–2, разделение train/validation/test и доступ к фактическим плотностям для оценки. Согласовать адаптер, не менять его внутреннюю реализацию.
2. С участником по обучению разобрать `model-choice.md` и `config.json`. Зафиксировать, что модель возвращает оценки до softmax, а нормализация выполняется один раз общим слоем.
3. Реализовать `model` и сохранение артефактов независимо от CSV. Проверить размеры входа и выхода, 3 651 параметр, один шаг обучения, сохранение и повторную загрузку одинаковых весов. Для этих технических проверок достаточно небольших искусственных тензоров; они не являются учебным набором проекта.
4. Подключить реальные данные через адаптер. Затем реализовать обучение и раннюю остановку, базовый алгоритм, метрики и отдельную оценку.
5. Добавить прогноз в существующее меню, зафиксировать зависимости и проверить установку на Ubuntu 24.04. Сохранить контрольный вход и эталонный результат по ТЗ.

## Разделение ответственности

Боря отвечает за архитектуру модулей, их совместимость, состав локальной инфраструктуры и единый запуск. Степа — за получение, генерацию, проверку и подготовку данных. Егор — за реализацию и обучение модели, эксперименты и содержательное сравнение результатов. Кирилл — за согласованность требований и материалов ТЗ. Границы реализации команда может уточнить, сохранив согласованные интерфейсы.

## Условия перехода к интеграции

Согласованы вход и выход каждого модуля, модель не зависит от конкретного CSV, параметры не противоречат ТЗ. Участник по данным может передать свой результат через адаптер, а участник по обучению — реализовать GRU без изменения меню и внешнего формата прогноза.

## Проверки полной программы

При интеграции проверяются отсутствие будущих значений во входе и test при обучении; размеры выборок; правила равенства минимумов и максимумов; метрики на примерах ТЗ; корректная загрузка весов в новом процессе; отклонение ошибочного ввода; прогноз на 12 строках без будущей строки; сумма вероятностей и контрольный JSON. Тестовая оценка должна содержать 31 568 решений обоих алгоритмов.

Текущий каркас проверяется отдельно: запуск из другой папки, вывод состояния в JSON, просмотр объяснения модели, отказ зарезервированных режимов с кодом 2 и отсутствие изменений существующих каталогов.
